# Physical-phone validation

The owner has now approved a fresh-install signing migration; use [the Android 1.8 setup](android-signing-setup.md). Wait until the new key is backed up, its certificate matches the server and the signed APK is ready before reinstalling on a test phone.

Physical validation requires an actual phone. This cloud workspace cannot access a USB phone attached only to your laptop. Android Studio is needed only on the test computer for SDK/ADB tools, not on employees' phones or computers. The APK runs on Android 9+; iPhones cannot install an Android APK. Desktop users use the HTTPS web app, while native Wi-Fi observation and workday background sharing require Android.

1. On the test laptop, install Android SDK Platform-Tools using Android Studio. Connect the Samsung phone by USB. Enable Developer options/USB debugging on the test phone and accept the computer's debugging prompt. Do not expose ADB to the public internet.
2. From the source folder, run `bash scripts/check-connected-phone.sh`. The script is read-only: it reports model, Android version, installed app version and location/notification permission states. It does not install/uninstall anything, read employee records, collect locations or change an account binding. Share only the resulting checks, never passwords/private keys. USB connection to your laptop does not automatically connect it to this cloud session.
3. Install/update only a signed APK whose signing certificate is approved and matches the installed app for an in-place update. The current unsigned release candidate is not installable and must not be passed off as an update. Do not uninstall the existing app to work around a mismatch without an agreed migration/recovery plan.
4. On the phone, validate your own registration/sign-in, email verification and HR approval. Enroll the actual phone passkey, complete a successful check-in, cancel a second prompt, and confirm no unintended attendance is recorded. The certificate/RP/asset-links association must match before this step can pass.
5. Have HR open a session. Refresh on the employee phone, mark attendance once, then verify the original receipt appears on the phone, computer history and authorized all-employees viewer. A duplicate manual override must preserve that original receipt. Confirm viewer-only accounts have no HR or movement access.
6. Verify that opening, signing in, viewing attendance and HR controls work away from the venue without requesting location. At submission, test the approved office connection, mobile data, wrong network, precise-location denial, stale/inaccurate GPS and an offsite position. Only a fresh onsite position plus the required connection and phone verification may create attendance. Check that no room-code controls or temporary setup notices appear. These signals still cannot prove a particular floor.
7. During 10:30–20:30 India time, give explicit daily sharing consent. Confirm the Android foreground notification appears, walk away and return, then stop sharing from both app and notification in separate tests. Repeat offline, with GPS disabled, after sign-out and after force-stop. Confirm no automatic next-day restart and no collection outside the workday. Android can interrupt delivery; missing intervals must remain unknown.
8. Compare the movement report with the known test walk: estimated venue/away time, crossing bounds, approximate stops, missing returns, unknown gaps and the partial-day cutoff. On the computer test search, department/date-range CSV and authorized read-only access in current Chrome/Edge/Firefox; test Safari separately if employees use it.

Passing automated tests or an emulator run does not substitute for these hardware checks. Record the app version, actual signing certificate, phone/Android version, deployment commit and pass/fail for each test. Do not record biometric templates, passwords or unrelated personal data in the test report.
